# ТЗ: алгоритмы взаимодействия с FluidNC и LinuxCNC (версия 2)

Пункты, которые нужно проверить на стенде, помечены `[V-N]` и собраны в разделе 9. До проверки такие пункты считаются предположениями и не реализуются как окончательные.

## 1. Контекст

В проекте уже есть базовая структура: типы, интерфейсы и, возможно, заготовки адаптеров. Задача: реализовать два алгоритма логического взаимодействия с системами ЧПУ (FluidNC и LinuxCNC) и интегрировать их в существующий код.

**Обязательное требование:** адаптеры используют существующие в проекте типы, трейты и модули. Новые типы вводятся только тогда, когда в проекте аналога нет, и это фиксируется в описании PR. Дублирование запрещено.

**Общий трейт.** Оба адаптера реализуют существующий трейт управления станком. Путь к нему исполнитель указывает в первом PR. Если трейта, покрывающего загрузку программы, старт, паузу, стоп, overrides, jog, home и подписку на события, в коде нет, исполнитель сообщает об этом до начала реализации и предлагает расширение существующего трейта. Создавать параллельный трейт нельзя.

## 2. Общие требования

- **Язык:** Rust, edition согласно `Cargo.toml` проекта.
- **Асинхронность:** tokio. Оба адаптера полностью асинхронны. В production-коде нет блокирующих вызовов и `std::thread::sleep`.
- **Ошибки:** в production-коде нет `unwrap()` и `expect()`. Ошибки типизированы и содержат понятное сообщение. Существующий тип ошибок проекта используется, если он есть.
- **Логирование:** через `tracing`. Покрываются подключение, отправка и получение строк, ответы контроллера, алармы, таймауты, reconnect. Содержимое программы в INFO не логируется.
- **Конфигурация:** все таймауты, размеры буферов, интервалы опроса и параметры backoff задаются в конфигурации. Значения по умолчанию приведены в разделе 4.
- **Завершение:** внутренние задачи останавливаются через `tokio_util::sync::CancellationToken`. Порядок при остановке: сначала прекращается отправка строк, затем задача приёма, затем закрывается сокет. При `drop` адаптера токен отменяется.
- **Публичный API:** минимальный, только то, что нужно UI. Задачи, каналы и внутренние структуры приватны.
- **Документация:** все публичные типы и функции имеют doc-комментарии.
- **Транспорт:**
  - FluidNC: WebSocket через `tokio-tungstenite`. TLS не используется по умолчанию, включается конфигом.
  - LinuxCNC: TCP через `tokio::net::TcpStream`.

## 3. Общая модель событий, снимка и ошибок

### 3.1. События

Адаптер публикует поток событий через `tokio::sync::broadcast`:

- `Connected` / `Disconnected { reason }`
- `StatusUpdate`
- `StateChanged { from, to }`
- `ProgramLineChanged(line)`
- `ProgramStarted` / `ProgramFinished`
- `Alarm { code, message }`
- `ProtocolError { code, message }`
- `OverrideChanged { kind, value }`

**Отставание подписчика.** При `RecvError::Lagged(n)` UI перечитывает актуальный снимок через `last_status()` и показывает предупреждение о пропущенных событиях. Состояние при этом не считается потерянным, потому что снимок всегда актуален.

### 3.2. Актуальный снимок

`last_status()` возвращает последний `MachineStatus` из `tokio::sync::watch::Receiver`. Метод неблокирующий. Подписка на изменения через `watch::Receiver::changed()` также доступна.

### 3.3. Предусловия команд

Адаптер проверяет предусловия по `last_status()`: например, `start()` при состоянии Running возвращает ошибку без отправки команды.

Снимок может быть устаревшим, поэтому такая проверка даёт только предварительный ответ. Окончательное решение принимает контроллер. Если контроллер вернул ошибку, она передаётся вызывающему коду как есть и не подавляется.

### 3.4. Ошибки операций

Тип ошибки содержит как минимум:

- `NotSupported` (операция не поддерживается системой);
- `InvalidState` (операция недопустима в текущем состоянии);
- `Timeout` (операция, с указанием этапа);
- `Protocol` (неожиданный или нераспознанный ответ);
- `Disconnected`;
- `Controller { code, message }` (ошибка, полученная от контроллера).

## 5. Алгоритм №1: FluidNC

### 5.1. Принцип

FluidNC работает как Grbl-подобный контроллер с буфером планировщика. Ответ `ok` означает, что строка принята в буфер и есть место для следующей. Он **не** означает, что движение по строке завершено.

**Жёсткое требование:** sender loop не ждёт физического завершения движения по строке. Ожидание ограничено только заполненностью буфера.

### 5.2. Классы команд

Команды делятся на два класса с разными путями отправки.

**Realtime (мимо очереди, сразу в сокет):**

| Команда | Действие | Ответ `ok` | Учитывается в буфере |
|---|---|---|---|
| `?` | запрос статуса | нет | нет |
| `!` | feed hold (пауза) | нет | нет |
| `~` | cycle start (возобновление) | нет | нет |
| `0x18` (Ctrl-X) | soft reset (остановка) | нет | нет |
| `0x85` | отмена jog | нет | нет |
| override-байты | изменение feed, spindle, rapid | нет | нет |

Коды override-байтов и поведение Ctrl-X и `0x85` подлежат проверке `[V-F2]`, `[V-F3]`.

**Line-команды (очередь sender loop):** строки G-code, `$J=...` и системные строки (`$H`, `$X`). Каждая учитывается в буфере и подтверждается `ok` или `error:N`.

Realtime-команды не должны ждать в очереди. Пауза и стоп выполняются немедленно, даже если очередь заполнена.

### 5.3. Character-counting

Правило буферизации (проверяется property-тестом):

- для каждой отправленной и неподтверждённой строки учитывается `len(line) + 1` (с учётом `\n`);
- сумма учитываемых длин не превышает `rx_buffer_bytes` ни в один момент времени;
- строка, которая не помещается, остаётся в очереди, пока не придёт `ok` и не освободит место;
- строка длиннее `max_line_len` отклоняется до отправки с ошибкой `Protocol`.

Счёт по количеству строк не используется.

**Соответствие `ok`.** Подтверждения идут в порядке отправки (FIFO). Каждый `ok` снимает самую старую неподтверждённую строку. `ok` без неподтверждённой строки фиксируется как `ProtocolError`, счётчик не уходит в минус.

### 5.4. Sender loop

- Берёт строку из очереди и отправляет её, если она помещается в буфер.
- Если не помещается, ждёт уведомления от receiver loop (`tokio::sync::Notify` или канал).
- **Пауза** (`!`): новые строки не отправляются, очередь и счётчики сохраняются. Возобновление через `~`.
- **Стоп:** очередь очищается, отправляется Ctrl-X, счётчик неподтверждённых строк сбрасывается. Сброс счётчика выполняется только после подтверждения сброса контроллера `[V-F3]`.
- **Аларм:** отправка прекращается. Неподтверждённые строки остаются в учёте до сброса контроллера.

### 5.5. Receiver loop

Каждый текстовый фрейм классифицируется:

- `ok` → снятие строки из учёта, уведомление sender loop, при необходимости `ProgramLineChanged`;
- `error:N` → `ProtocolError` и политика из 5.6;
- `ALARM:N` → `Alarm`, немедленная остановка отправки;
- статус (`<...>`) → парсинг, обновление `watch`, `StatusUpdate`, при смене состояния `StateChanged`;
- `[MSG:...]`, `[GC:...]`, `$...` и прочие служебные строки → логируются и передаются событием, если это предусмотрено;
- всё, что не распознано, → WARN в лог, без падения.

**Формат статуса.** Текущая спецификация ТЗ описывает JSON-статус. По известному мне описанию FluidNC статус текстовый, в формате Grbl (`<Idle|MPos:...|FS:...>`). Итоговый формат фиксируется по фикстурам, снятым со стенда `[V-F4]`. Парсер поддерживает только подтверждённый формат. Неподтверждённый формат не реализуется.

### 5.6. Политика ошибок при стриминге

**Решение по умолчанию (предложение, требует утверждения владельцем продукта):** при `error:N` посреди программы отправка новых строк останавливается, программа переходит в состояние `Stopped` с ошибкой, UI получает `ProtocolError` с номером строки. Продолжить можно только явным действием пользователя: отмена (Ctrl-X) или повторный запуск с выбранной строки.

Пропуск строки и автоматическое продолжение не реализуются без отдельного решения.

### 5.7. Reconnect во время стриминга

Сброс `unacked` и очистка очереди при переподключении **запрещены** без проверки состояния.

Порядок после переподключения:

1. Отправить `?` и прочитать состояние, включая поле буфера (`Bf:`) `[V-F6]`.
2. Если контроллер в Idle и буфер пуст, локальные счётчики сбрасываются, программа считается завершённой или прерванной.
3. Если контроллер в Run или Hold, и в буфере есть строки, программа переходит в состояние `Detached`. Адаптер не знает, какие строки получили `ok` до разрыва, поэтому состояние помечается как неизвестное.
4. В состоянии `Detached` пользователь выбирает: отменить (Ctrl-X) или дождаться окончания движения. Отправка новых строк из очереди не возобновляется без подтверждения.

Точный алгоритм восстановления зависит от результатов `[V-F6]`.

### 5.8. Jog

- `$J=...` отправляется как line-команда.
- Jog во время стриминга программы запрещён (`InvalidState`).
- Отмена jog выполняется realtime-байтом `0x85` `[V-F2]`, без очереди.
- Если jog не поддерживается конфигурацией контроллера, возвращается `NotSupported`.

### 5.9. Overrides

Overrides передаются realtime-байтами `[V-F2]`. Изменение подтверждается через `OverrideChanged` после прихода статуса. Коды и диапазоны сверяются со стендом.

### 5.10. Маппинг состояний

Таблица строится по фикстурам статуса `[V-F4]`. Целевые состояния UI: Disconnected, Idle, Run, Hold, Jog, Home, Alarm, Door, Check, Sleep. Значения состояний контроллера, которые не входят в таблицу, переводятся в `Unknown` с записью в лог.

### 5.11. Загрузка программы

`load_program(source)`, где `source` — путь к файлу или строка:

1. Файл читается построчно, строки нормализуются (пробелы и комментарии). Пустые строки и комментарии не отправляются.
2. Строки кладутся в очередь sender loop.
3. Метод возвращает управление сразу и не ждёт окончания отправки.
4. Ошибки разбора, превышение `max_line_len` и запрещённые символы обнаруживаются до постановки в очередь и возвращаются как ошибка метода.

## 6. Алгоритм №2: LinuxCNC

### 6.1. Принцип

LinuxCNC имеет собственный интерпретатор G-code. UI не стримит строки. Программа передаётся на сервер целиком, сервер её проверяет и выполняет. UI опрашивает снимок состояния.

### 6.2. Транспорт и владелец соединения

Один TCP-сокет к `linuxcncrsh` (порт 5007 по умолчанию).

**Обязательная архитектура:** единственная задача-актор владеет сокетом. Команды приходят через `mpsc`, каждая содержит ответный канал `oneshot`. Ответы сопоставляются с командами по маркеру завершения. Управляющая задача и poller не работают с сокетом напрямую.

Формат маркера завершения (например, `<n> done`, `<n> ready`) и механизм сопоставления подлежат проверке `[V-L1]`.

**Приоритет.** Команды пользователя выполняются раньше poll. Если команда ожидает в очереди, очередной `update` откладывается.

### 6.3. Команды

Имена команд из версии ТЗ 1 сверяются с документацией linuxcncrsh. Ниже перечислены команды, которые ТЗ использует, и статус их проверки:

| Действие | Команда (по ТЗ) | Статус |
|---|---|---|
| Сессия | `hello <user> <passwd> <version>` | `[V-L1]` |
| Загрузка | `load <file_path>` | `[V-L2]` (возможно иное имя) |
| Режим | `set mode auto` | `[V-L1]` |
| Выполнение | `set task execute` | `[V-L1]` |
| Старт / пауза / возобновление / стоп | `run`, `pause`, `resume`, `abort` | `[V-L1]` |
| Overrides | `set feed|spindle|rapid <percent>` | `[V-L1]` |
| Статус | `update <seq>` | `[V-L1]` |
| Аварийная остановка (только sim) | `set estop 1` / `set estop 0` | `[V-L6]` |
| Jog, home | неизвестно | `[V-L7]` |

Если команда jog или home в linuxcncrsh не найдена, операция возвращает `NotSupported`.

### 6.4. Загрузка программы

- **Путь к файлу:** передаётся как есть. Файл должен быть доступен серверу LinuxCNC, а не клиенту. Адаптер проверяет это ответом сервера, а не локальным `exists()`.
- **Inline-содержимое:** способ передачи файла на сервер не определён. Допустимые варианты, которые нужно проверить `[V-L2]`:
  - механизм самого linuxcncrsh для записи файла;
  - общий каталог, доступный и клиенту, и серверу;
  - отказ с `NotSupported`, если ни один вариант не подтверждён.

  Временный файл на клиенте без передачи на сервер не используется. Удаление временного файла выполняется только на той стороне, где он создан.
- **Проверка синтаксиса:** ответ на `load` разбирается. Если сервер сообщил об ошибке, программа не запускается и возвращается `Controller { ... }` с текстом ответа. Формат ошибки в ответе `[V-L3]`.

### 6.5. Poller

- Каждые `poll_interval` отправляется `update <seq>`. `seq` увеличивается на каждый запрос.
- Ответ многострочный и разбирается по именам блоков `EMC_*_STAT`, а не по пустым строкам или маркерам. Блоки разбираются по фикстурам `[V-L4]`.
- Неполный ответ (нет маркера завершения, обрыв) отбрасывается целиком. Частичные данные в снимок не попадают.
- Неизвестные блоки игнорируются с записью в лог.
- Ошибка парсинга одного блока не отменяет остальные блоки и фиксируется как `ProtocolError`.

### 6.6. Маппинг состояний

Состояние UI вычисляется из `state`, `task_state` и `interp_state`. Черновик таблицы (**требует проверки и уточнения по фикстурам `[V-L4]`**):

| `state` | `task_state` | `interp_state` | Состояние UI |
|---|---|---|---|
| Estop | любое | любое | Estop |
| EstopReset | любое | любое | EstopReset |
| On | Idle | Idle | Idle |
| On | Running | Reading / Waiting | Running |
| On | Paused | любое | Paused |
| On | любое | Не распознано | Unknown с записью в лог |

Все строки таблицы подтверждаются фикстурами. Неподтверждённые строки не реализуются.

Состояние `Disconnected` вычисляется самим адаптером, а не контроллером.

### 6.7. Reconnect

1. Повторная `hello`.
2. Восстановление режима (`set mode auto`).
3. Запрос статуса. Если программа уже загружена в интерпретатор, она не загружается повторно `[V-L5]`.
4. Публикуется `Connected`.

Сохраняется ли программа в интерпретаторе после разрыва сессии, проверяется `[V-L5]`.

### 6.8. Аварийная остановка

Команда `set estop` существует только в sim и не соответствует физической кнопке. Сценарий E-Stop на стенде проверяет только программную аварийную остановку. См. раздел 8.

## 7. Критерии приёмки

Числовые значения ниже — предложения. Владелец продукта утверждает их до начала работы.

**Общие:**
- `cargo test` (без `#[ignore]`) проходит, `cargo clippy -D warnings` проходит, `unwrap()`/`expect()` в production-коде отсутствуют (проверяется grep по `src/` в CI).
- Все публичные типы и функции имеют doc-комментарии.
- Все таймауты и размеры буферов берутся из конфига.

**FluidNC:**
- Property-тест: сумма учитываемых байт неподтверждённых строк не превышает `rx_buffer_bytes` ни на одном шаге (минимум 10 000 случайных последовательностей).
- Realtime-команда (`!`, `?`) уходит в сокет в течение 10 мс от вызова при свободном сокете (проверка на стенде).
- На стенде при стриминге короткой программы из 200 строк буфер контроллера заполнен не менее чем на 50 % в установившемся режиме. Порог проверяется по статусу `Bf:` `[V-F6]`.
- Пауза и стоп выполняются при заполненной очереди без ожидания освобождения буфера.

**LinuxCNC:**
- Poller не отправляет `update`, если команда ожидает в очереди.
- Неполный ответ `update` не меняет последний снимок.
- Reconnect: состояние адаптера совпадает с состоянием сервера в пределах 5 с после восстановления связи.

**Задержка E-Stop (только если стенд её измеряет):** время от команды до события `Alarm`/`Estop` измеряется и записывается в отчёт. Порог устанавливается после первого измерения на стенде и утверждается владельцем продукта. Порог заранее не назначается.

## 8. Тестирование

### 8.1. Unit-тесты

- Парсинг ответов FluidNC: `ok`, `error:N`, `ALARM:N`, статус, служебные строки. Фикстуры по версии прошивки.
- Парсинг многострочного `update` LinuxCNC по блокам `EMC_*_STAT`. Фикстуры по версии LinuxCNC.
- Маппинг состояний (обе системы).
- Character-counting: property-тест из раздела 7.
- Backoff reconnect: последовательность задержек и лимит попыток.
- Логика буфера на in-memory каналах, без сети.

### 8.2. Фикстуры

- Каждая фикстура хранится в `tests/fixtures/<система>/<версия>/` вместе с датой снятия и описанием стенда.
- Фикстуры снимаются скриптом с реального стенда, а не пишутся вручную.
- При обновлении прошивки или LinuxCNC фикстуры переснимаются, а старые версии сохраняются.

### 8.3. Интеграционные тесты на стендах

Помечаются `#[ignore]`. Запуск: `cargo test -- --ignored`.

Адреса задаются переменными окружения: `FLUIDNC_URL`, `LINUXCNC_HOST`, `LINUXCNC_PORT`.

**Если переменная не задана, тест не проходит молча.** Он завершается с явным сообщением о пропуске (`skipped: FLUIDNC_URL not set`), которое видно в выводе.

**Стенд FluidNC:** ESP32 с FluidNC, Wi-Fi. Движение не моделируется физически. Для проверки счётчиков и входов можно подключить модель станка из предыдущих обсуждений, если она будет готова.

**Стенд LinuxCNC:** Linux-машина, LinuxCNC в режиме sim (`sim/axis/axis.ini`), `linuxcncrsh` слушает порт.

**Сценарии:**

1. Подключение и проверка соединения.
2. Загрузка короткой программы (G0/G1/M2).
3. Запуск и ожидание `ProgramFinished`.
4. Проверка, что `current_line` менялся во время выполнения.
5. Пауза и возобновление в середине программы.
6. Установка overrides и проверка через `last_status()`.
7. Разрыв соединения и проверка `Disconnected` и последующего `Connected`:
   - LinuxCNC: остановка процесса `linuxcncrsh` на стенде;
   - FluidNC: отключение Wi-Fi со стороны стенда (точка доступа или управление питанием платы через реле). Сам ESP32 не выключается из кода адаптера.
8. Программная аварийная остановка:
   - LinuxCNC sim: `set estop 1`, проверка события и состояния `Estop`, затем `set estop 0` и проверка `EstopReset`. Этот сценарий не проверяет физическую кнопку.
   - FluidNC: `Alarm` при подаче команды, которая вызывает аларм на стенде. Точная команда подлежит проверке `[V-F7]`.
9. (FluidNC, при наличии модели станка) проверка соответствия числа отправленных шагов и числа шагов, полученных моделью.

Интеграционные тесты перед запуском проверяют, что стенд отвечает. Если стенд не отвечает, тест завершается с ошибкой окружения, а не с ошибкой адаптера.

## 9. Требуемые проверки на стенде

Каждый пункт проверяется до реализации соответствующего фрагмента. Результат записывается в фикстуры и в описание PR.

| ID | Что проверить | Чем подтверждается |
|---|---|---|
| V-F1 | Размер приёмного буфера FluidNC и поведение character-counting | Стриминг на стенде, наблюдение `Bf:` |
| V-F2 | Коды realtime-байтов для overrides, отмены jog (`0x85`) и поведения при их получении | Захват трафика, сравнение с документацией прошивки |
| V-F3 | Что делает Ctrl-X: сбрасывает ли буфер планировщика, отвечает ли контроллер | Захват трафика при остановке во время стриминга |
| V-F4 | Формат статуса: текстовый или JSON, набор полей, наличие `WCO:` и `Bf:` | Фикстуры статуса при разных состояниях |
| V-F5 | Требуется ли пароль для WebSocket и как он передаётся | Попытка подключения со стенда |
| V-F6 | Что показывает `?` после переподключения при Run и Hold, как читается `Bf:` | Стенд: разрыв во время стриминга, фиксация ответов |
| V-F7 | Команда, которая вызывает `ALARM` на стенде | Проверка на стенде |
| V-L1 | Имена и синтаксис команд linuxcncrsh, формат ответа и маркер завершения | Документация linuxcncrsh и захват трафика `telnet` |
| V-L2 | Способ загрузки программы по inline-содержимому | Проверка доступных команд linuxcncrsh на стенде |
| V-L3 | Формат ответа `load` при синтаксической ошибке | Загрузка заведомо неверной программы на стенде |
| V-L4 | Полный набор блоков `EMC_*_STAT` и значения `state`, `task_state`, `interp_state` | Фикстуры `update` в разных состояниях |
| V-L5 | Сохраняется ли программа в интерпретаторе после разрыва сессии | Стенд: загрузка, разрыв, повторное подключение |
| V-L6 | Поведение `set estop` в sim и проверка состояний | Захват трафика |
| V-L7 | Наличие команд jog и home в linuxcncrsh | Документация и проверка на стенде |

Если проверка показала, что команды или формат отличаются от ТЗ, исполнитель не подгоняет реализацию под ТЗ, а сообщает о расхождении и вносит исправление в ТЗ.

## 10. Определение готовности

Работа считается завершённой, когда:

- все пункты раздела 9 имеют результат проверки или явное решение «не проверено, не реализовано»;
- проходят unit-тесты и property-тест;
- интеграционные сценарии из раздела 8.3 проходят на стендах или явно помечены как не выполненные с причиной;
- критерии раздела 7 выполнены или отклонения задокументированы;
- политика ошибок (5.6) и политика reconnect во время стриминга (5.7) утверждены владельцем продукта.
