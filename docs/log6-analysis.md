# Анализ `log6.txt`: скачок позиции на дуге FluidNC

**Причина найдена в последовательности обработки команд адаптером.** В `FluidNcWebSocketAdapter::status()` после получения статуса `Idle` вызывается `send_next_program_line()`. Эта функция отправляет строку программы через `send_command()` и ждёт ответа `ok`. Пока адаптер ждёт подтверждение, `send_command()` читает и отбрасывает промежуточные статусные сообщения FluidNC. Поток контроллера в это время не может продолжить опрос статуса.

Для дуги FluidNC может прислать `ok` только ближе к её завершению. Поэтому приложение какое-то время показывает прежнюю позицию, а после подтверждения получает актуальные координаты — отсюда резкий скачок ближе к концу дуги. Переход номера строки с 10 на 11 в диагностике согласуется с тем, что строка программы считается подтверждённой только после получения `ok`.

## Предлагаемое исправление

Изменить потоковую отправку G-code в `cnc_core/src/adapters/fluidnc_websocket.rs` так, чтобы ожидание `ok` не блокировало чтение статусов:

- отправлять строку программы без ожидания подтверждения внутри `status()`;
- хранить состояние одной неподтверждённой строки;
- продолжать читать статусы `Run` во время движения и обрабатывать `ok` отдельно;
- отправлять следующую строку только после подтверждения текущей строки и завершения движения (`Idle`).

Для корректного flow control одновременно должна оставаться отправленной не более чем одна строка G-code. После исправления повторить тот же тест и проверить, что `[ARC DIAG]` показывает меняющиеся координаты с начала дуги.
