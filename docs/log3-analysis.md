По `log3.txt` видно, что FluidNC передаёт статусы во время выполнения дуги: после перехода в `Run` координаты `MPos` последовательно меняются по траектории и доходят до конца дуги. Значит, причина не в том, что ESP32 не отправляет телеметрию в начале движения.

В логе также есть несколько ответов `Idle` между отправкой `G2` и началом `Run`. Это задержка до фактического начала движения; она сама по себе не объясняет скачок фрезы ближе к концу дуги.

Следующая проверка — сравнить эти статусы с тем, что получает браузер. Запустите приложение с включённой трассировкой HTTP-ответов:

```bash
CNC_UI_FLUIDNC_WS_TRACE=1 CNC_UI_HTTP_STATUS_TRACE=1 CNC_UI_CONFIG=config/fluidnc-test.yaml cargo run -- --web
```

Во время дуги найдите в терминальном выводе строки `[HTTP STATUS]` и проверьте поля `x`, `y`, `z`, `current_line`, `state`. Если координаты в них изменяются плавно, а фреза в 3D стоит, задержка возникает уже в браузерном обновлении/отрисовке. Если HTTP-координаты тоже скачут, будем искать проблему между FluidNC-адаптером и HTTP-статусом.
