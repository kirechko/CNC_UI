# Предложения по синхронизации

## 1. Статус контроллера: `Mutex` → `RwLock`

В `CNCController` поле `status` читается часто для формирования снимка и обновляется одним worker-потоком. `std::sync::RwLock<ControllerSnapshot>` позволит нескольким читателям одновременно получать снимок, сохранив эксклюзивную запись.

Замена оправдана, если измерения покажут конкуренцию за блокировку. Сейчас критические секции короткие, а `get_status_snapshot()` клонирует статус под блокировкой, поэтому выигрыш может быть небольшим. Не держать read/write guard во время I/O, `await` или вызова API. Учесть, что `RwLock` не гарантирует одинаковую справедливость на всех платформах.

## 2. SQLite: не заменять `Mutex<Connection>` автоматически

Одна `rusqlite::Connection` сериализует запросы и записи, что нормально для небольшого журнала. Замена на `RwLock` сама по себе не даст параллельных запросов: SQLite-соединение и его доступ всё равно нужно синхронизировать. Если чтение журнала начнёт задерживать записи, рассмотреть отдельные read-only соединения для запросов и одно соединение для записей либо очередь записи.

## 3. Останов и отмена: избежать общего сбрасываемого `AtomicBool`

Схема «установить `true` при Stop, затем сбросить в `false` при запуске команды» подвержена потере сигнала: Stop может произойти между проверкой/сбросом флага и фактическим запуском команды. Отдельные флаги отмены команды и остановки движения также могут разойтись по состоянию.

Лучше выдавать каждой выполняемой команде собственный токен отмены и хранить токен только активной команды. Stop отменяет этот токен и отправляет приоритетный запрос остановки; запуск следующей команды создаёт новый токен, не сбрасывая сигнал предыдущей. Для Tokio можно рассмотреть `CancellationToken` из `tokio-util`, если зависимость приемлема; иначе — канал/событие с идентификатором команды.

Важно: обычная очередь команд не должна быть единственным каналом Stop. Если worker блокируется внутри долгого вызова API, он не сможет обработать Stop из той же очереди. Адаптер должен поддерживать отмену ожидания и отдельный безопасный путь для realtime/feed-hold остановки. Отмена ожидания ответа на команду не всегда отменяет уже исполняемое станком движение.

## Рекомендуемый порядок

1. Сначала уточнить и покрыть тестами семантику Stop и отмены активной команды.
2. Устранить сбрасываемые глобальные флаги в пользу токена/события для конкретной команды.
3. Только затем заменить статусный `Mutex` на `RwLock`, если профилирование подтверждает пользу.
4. SQLite оставить на `Mutex`, пока нет измеренной проблемы с конкуренцией.
